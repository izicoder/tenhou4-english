## How the tile labels work (write this into notes/tiles.md, it is your reference)
- Tile sprite key = sheet | slot<<8 | face<<16 | seat<<24. Sheets: 116 hand, 121 wall, 107 discards, 110 melds/dora.
- Face index: 0/10/20 = red 5m/5p/5s, 1-9 man, 11-19 pin, 21-29 sou, 30-33 = E S W N, 34 = white dragon (also the blank base tile), 35 green, 36 red, 37 = tile back, 38/39 = shadow variants.
- Sprites live in obj0..obj3 .dat files: u32 magic ('obj0'..'obj3'), u32 structSize (103780 for obj0/obj2, 3856 for obj1/obj3; obj1/obj3 have 3 extra floats), then a u32 pointer table up to structSize. Each record: i16 x,y,w,h; u32 key; u32 (skipped); u32 dataLen; zlib data at record+20. Sheet 110 slots are remapped (see normalizeKey).
- The client builds one sprite in Ac.zb(): Zlib.Inflate(base tile, face 34) -> Inflate(face artwork delta, if face != 34) -> Inflate(shadow, face 38/39) -> new ImageData -> putImageData on a per-slot canvas. That canvas is re-decoded (and wiped) whenever its face changes.
- Our module wraps Zlib.Inflate to learn which face is being decoded, and CanvasRenderingContext2D.prototype.putImageData to draw the label right after. The label rect is the union of all face artwork rects for that slot, relative to the base tile.

## Task B: known bug to fix (before live testing)
GROUPS (the per-slot artwork union) is keyed only by sprite key and is global. When the browser window is resized the client downloads the sprite files again at a new resolution, with different coordinates, and the union then mixes both resolutions, so labels can drift. Fix it: keep one groups map PER parsed buffer (store it next to the per-buffer offset table), carry that map in curSprite, and use it in makeJob. Add a unit test that parses two buffers with the same keys but different coordinates and checks each gets its own rect.
